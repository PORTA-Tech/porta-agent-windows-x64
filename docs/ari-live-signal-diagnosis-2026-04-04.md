# Ari Live Signal Diagnosis

Date: 2026-04-04

## Scope

This diagnosis covers the Ari service, `Porta.UserAgent`, the local API, the desktop widget, and the control center.

The immediate user-visible complaints were:

- Ari often fails to connect to the local API.
- Ari falls back to cached snapshots instead of live signals.
- The widget and control center disagree about what is happening now.
- The system has been unstable for about a week and is difficult to recover manually.

## Executive Summary

The main problem is not one single bug. Ari currently has multiple partially independent "truth" pipelines:

1. `Porta.UserAgent` publishes durable input windows through `/v1/input/signals`.
2. `Porta.UserAgent` also publishes a separate live-session stream through `/v1/session/live`.
3. The service's main `AgentBrainSnapshot` path is generated by a different pipeline entirely and is not driven by the user-agent's real live input windows.

Those pipelines can stall or drift independently. When that happens:

- the local API can still be alive while `/v1/status`, `/v1/snapshot/current`, and `/v1/session/live` are stale or timing out,
- the widget can report cached or mixed state,
- the control center can keep showing prior values,
- the watchdogs can still think the user-agent is "healthy" because the heartbeat file is updating.

The single biggest architectural defect is that Ari's current snapshot path is still built from synthetic service-side signals instead of the user-agent's live capture stream.

## Defects To Fix

## 1. Current snapshot path is not driven by real user-agent live signals

Evidence:

- [`src/Porta.Agent.Core/AgentBrainPipeline.cs`](../src/Porta.Agent.Core/AgentBrainPipeline.cs) `SystemSignalAcquisitionStage` uses `Process.GetProcesses().Length` plus `sin`/`cos` waves instead of user-agent input windows.
- [`src/Porta.Agent.Core/AgentBrainPipeline.cs`](../src/Porta.Agent.Core/AgentBrainPipeline.cs) lines around `69-77`.
- [`src/Porta.Agent.Core/AgentBrainWorker.cs`](../src/Porta.Agent.Core/AgentBrainWorker.cs) writes snapshots from that synthetic acquisition path and applies them as the service's current snapshot.
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) builds status from `_latestSnapshot` for `FocusStrength`, `OverloadLikelihood`, and `LastAction`.
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) `GetCurrentSnapshot()` returns `_latestSnapshot` directly.

Impact:

- Ari's "current" snapshot is not truly the user's live captured behavior.
- The status endpoint mixes synthetic snapshot values with real bucket-derived metadata, which guarantees incoherence.
- The widget and control center cannot be made reliable while they are reading from a split-brain model.

Required fix:

- Replace the synthetic `SystemSignalAcquisitionStage` path as the source of current analysis, or explicitly demote/remove it.
- Make the primary current snapshot derive from finalized or near-real-time user-agent capture data.
- Add a regression test proving that current snapshot values move when real input windows move.

## 2. Live session, durable input windows, and analyzed state are separate unsynchronized pipelines

Evidence:

- Durable input windows are sent in [`src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs`](../src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs) `FlushSignalsAsync()`.
- Live session state is sent separately in [`src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs`](../src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs) `PublishLiveSessionStateIfDueAsync()`.
- Durable input windows were still being inserted after the analyzed `brain_snapshots` stopped advancing.
- `state_buckets`, `input_signal_windows`, and `brain_snapshots` had different latest timestamps in the live database.

Impact:

- Ari can look "alive" in one path and "dead" in another.
- Widget, control center, and local API can each display a different reality.

Required fix:

- Define one authoritative "now" model.
- Explicitly document how live session, input windows, and current analysis relate.
- Either unify the paths or expose their health separately instead of silently blending them.

## 3. Local API request paths can stall or time out under controller lock contention

Evidence:

- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) uses a single `_gate` lock for status, live session, ingest validation, runtime-state refresh, and multiple DB-touching paths.
- Runtime-state refresh uses a `100 ms` `TryEnter` timeout and silently returns if it cannot acquire the lock.
- `ApplyBrainSnapshot()` does DB-backed refresh and diagnostics work while holding the same controller lock.
- Repeated direct probes to `/v1/session/live` timed out during diagnosis.
- Status freshness stopped advancing without any `runtimeStateRefreshError`, which is consistent with refresh starvation rather than an explicit handled failure.

Key source anchors:

- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) lines around `51-54`
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) lines around `297-307`
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) lines around `1404-1416`
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) lines around `1654-1681`
- [`src/Porta.Agent.Core/AgentCoreController.cs`](../src/Porta.Agent.Core/AgentCoreController.cs) lines around `2975-3048`

Impact:

- Local API appears flaky or unreachable even when the process is still up.
- Status/snapshot freshness decays into cached fallback mode.
- User experience matches "Ari cannot connect to the local API".

Required fix:

- Remove long DB work from the controller hot lock.
- Split "current in-memory state" from "DB-backed refresh and diagnostics".
- Add timing instrumentation per endpoint and per controller lock wait.
- Surface lock-starvation as an explicit degraded reason instead of silent staleness.

## 4. Live-session publish failures are largely silent

Evidence:

- [`src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs`](../src/Porta.UserAgent/UserAgentHost/UserAgentHost.cs) logs live-session publish failure only at debug level.
- [`src/Porta.Agent.LocalApi/LocalApiClient.cs`](../src/Porta.Agent.LocalApi/LocalApiClient.cs) `SendLiveSessionStateAsync()` catches exceptions and returns `null`.
- The durable input publish path has detailed diagnostic ack messages, but the live-session path does not.

Impact:

- Ari can lose live-session updates without any useful production signal explaining why.
- Widget freshness can degrade without actionable logs.

Required fix:

- Make live-session transport failures produce structured warnings with reason codes.
- Add last live-session publish attempt/result timestamps to diagnostics.
- Treat repeated live-session publish failures as a first-class health signal.

## 5. Heartbeat file persistence is using a fixed temp file path and is colliding during restarts

Evidence:

- [`src/Porta.Agent.Common/UserAgent/UserAgentSessionContextStore.cs`](../src/Porta.Agent.Common/UserAgent/UserAgentSessionContextStore.cs) writes to `_path + ".tmp"`.
- Logs show repeated `IOException` on `user-agent-session-context.v1.json.tmp` being used by another process.

Impact:

- False `missing_heartbeat` and `stale_heartbeat` decisions.
- Unnecessary user-agent restarts.
- More contention and instability in the whole capture system.

Required fix:

- Change heartbeat writes to use unique temp file names and atomic replace.
- Add process identity to collision logs.
- Add a test that simulates overlapping writes during restart/handover.

## 6. Two different watchdogs own the same user-agent process

Evidence:

- The service runs [`src/Porta.Agent.Service/CurrentSessionUserAgentWatchdog.cs`](../src/Porta.Agent.Service/CurrentSessionUserAgentWatchdog.cs).
- The control center independently runs [`src/Porta.ControlCenter/CurrentSessionUserAgentLauncher.cs`](../src/Porta.ControlCenter/CurrentSessionUserAgentLauncher.cs).
- [`src/Porta.ControlCenter/App.xaml.cs`](../src/Porta.ControlCenter/App.xaml.cs) starts a watchdog timer for the control center path.
- Both sides evaluate health and both can terminate/relaunch `Porta.UserAgent`.

Impact:

- Competing restart decisions.
- Recovery loops become self-inflicted instability.
- Ownership of heartbeat/session/live state becomes unclear.

Required fix:

- Pick one owner for process lifetime management.
- If the control center still needs visibility, make it observe only, not restart.
- Add explicit "watchdog owner" rules to architecture docs and tests.

## 7. Widget and control center intentionally keep different truth models

Evidence:

- [`src/Porta.ControlCenter/MainWindow.xaml.cs`](../src/Porta.ControlCenter/MainWindow.xaml.cs) preserves previous status/snapshot/live payloads when fresh fetches fail.
- The same file explicitly presents "Service alive, using cached snapshot."
- [`src/Porta.UserAgent/Interventions/UserDesktopWidgetStateBuilder.cs`](../src/Porta.UserAgent/Interventions/UserDesktopWidgetStateBuilder.cs) shows a different cached-snapshot explanation and uses a different combination of snapshot/status/live-session data.

Impact:

- The widget and control center disagree even when reading the same service.
- Users see "messy" synchronization problems that are actually designed into the state adapters.

Required fix:

- Define a single shared "what is happening now" DTO/adapter.
- Stop reusing previous payload objects silently in the control center.
- Carry freshness and degraded reason explicitly to both surfaces.

## 8. Service-side failures are poorly observable

Evidence:

- [`src/Porta.Agent.Core/BucketFinalizerWorker.cs`](../src/Porta.Agent.Core/BucketFinalizerWorker.cs) logs worker failures with `Console.WriteLine`.
- `service-core.log` was not keeping up with current runtime activity during diagnosis.
- Important paths such as bucket finalizer failure, live-session publish failure, and local API timeout behavior do not reliably land in persistent logs.

Impact:

- Real failures happen with almost no durable evidence.
- Diagnosis depends on indirect symptoms and database inspection.

Required fix:

- Route all service worker failures to persistent structured logs.
- Add endpoint latency logging for `/v1/status`, `/v1/snapshot/current`, `/v1/session/live`, and `/v1/input/signals`.
- Add counters for publish success/failure and finalizer progress.

## 9. Historical schema/migration regressions around `input_signal_windows` need a guardrail

Evidence:

- `service-core.log` contains long runs of `SQLite Error 1: 'no such table: input_signal_windows'`.

Impact:

- Missing schema during startup can poison diagnostics and freshness behavior.
- It is a known regression class and should not be allowed to recur silently.

Required fix:

- Add startup validation that refuses degraded runtime if critical tables are missing.
- Add migration smoke tests covering `input_signal_windows`.

## Fix Order

1. Unify Ari's source of truth. Current snapshot must come from real user-agent capture, not synthetic service-side signals.
2. Remove dual watchdog ownership. Keep restart authority in one place only.
3. Fix heartbeat file atomic write collisions with unique temp names.
4. Break controller lock contention by moving DB-backed refresh/diagnostics off the hot lock and adding timing telemetry.
5. Make live-session publish failures visible and diagnosable.
6. Unify widget/control-center state adapters so both show the same freshness and degraded reasons.
7. Add persistent logging for bucket finalizer, local API endpoint latency, and publish outcomes.
8. Add migration/startup guardrails so missing `input_signal_windows` cannot slip through again.

## Immediate Repair Plan

If work starts now, the first implementation sequence should be:

1. Replace or bypass the synthetic `SystemSignalAcquisitionStage` path for current snapshot generation.
2. Remove control-center restart authority and leave process recovery to the service watchdog only.
3. Fix `UserAgentSessionContextStore.WriteCurrent()` temp-file handling.
4. Add structured diagnostics for live-session publish failures and local API endpoint latency.
5. Refactor controller lock usage around runtime-state refresh and diagnostics writes.
6. Replace separate widget/control-center "now" adapters with one shared adapter.

## Open Questions To Verify While Fixing

- Whether the installed binaries exactly match the current source, because historical `widget_unavailable` restart evidence does not appear in the current recovery evaluator source.
- Whether bucket finalizer progress is currently failing silently after `input_signal_windows` ingestion, because worker exceptions are not durably logged.
- Whether local API request stalls are primarily controller-lock starvation, SQLite contention, or both.
